01_race.c

Race Condition: counter++ Tanpa Proteksi

Dua thread masing-masing increment 1.000.000 kali tanpa lock. Hasilnya tidak bisa diprediksi dan hampir selalu kurang dari 2.000.000.

race condition LOAD–ADD–STORE lost update non-determinism
Kenapa hasilnya kurang dari 2.000.000? counter++ bukan satu instruksi — CPU melakukan tiga langkah: LOAD (baca dari memori), ADD (tambah di register), STORE (tulis balik). Jika T1 di-preempt setelah LOAD dan sebelum STORE, T2 membaca nilai lama yang sama — satu update hilang (lost update).
Yang perlu diobservasi
  1. Jalankan ./race tiga kali berturut-turut — apakah hasilnya sama setiap kali?
  2. Berapa selisih dari 2.000.000? Apakah selisihnya konsisten?
  3. Coba jalankan dengan -O2 (optimasi compiler) — apakah hasilnya berbeda?
/*
 * 01_race.c – Race Condition pada counter++
 * Compile: gcc -Wall -pthread -O0 -o race 01_race.c
 * Jalankan beberapa kali dan amati: hasilnya tidak selalu 2.000.000.
 */
#include <stdio.h>
#include <pthread.h>

#define LOOP 1000000

int counter = 0; /* shared, tidak dilindungi */

void *increment(void *arg) {
    for (int i = 0; i < LOOP; i++) {
        counter++; /* LOAD, ADD, STORE — tidak atomik! */
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;

    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);

    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    printf("Ekspektasi : %d\n", LOOP * 2);
    printf("Hasil nyata: %d\n", counter);

    if (counter == LOOP * 2)
        printf("STATUS: Kebetulan benar — coba jalankan lagi.\n");
    else
        printf("STATUS: Race condition! Kehilangan %d update.\n",
               LOOP * 2 - counter);

    return 0;
}
02_mutex.c

Solusi Mutex: pthread_mutex_lock / unlock

Program yang sama, tapi counter++ dilindungi mutex. Hasilnya selalu tepat 2.000.000 — mutex menjamin mutual exclusion.

mutex pthread_mutex_lock critical section mutual exclusion blocking wait
Cara kerja mutex: saat pthread_mutex_lock dipanggil dan lock sudah diambil thread lain, OS menidurkan thread pemanggil — thread tidak memakan CPU selama menunggu. Saat lock dilepas, OS membangunkan thread berikutnya dari antrian.
Yang perlu diobservasi
  1. Jalankan ./mutex tiga kali — apakah hasilnya selalu 2.000.000?
  2. Bandingkan waktu: time ./race vs time ./mutex — mana lebih cepat?
  3. Coba pindahkan lock/unlock ke luar loop — apa yang berubah dari sisi kebenaran dan kecepatan?
/*
 * 02_mutex.c – Perbaikan dengan pthread_mutex
 * Compile: gcc -Wall -pthread -O0 -o mutex 02_mutex.c
 * Hasilnya harus selalu tepat 2.000.000.
 */
#include <stdio.h>
#include <pthread.h>

#define LOOP 1000000

int counter = 0;
pthread_mutex_t lock; /* variabel mutex */

void *increment(void *arg) {
    for (int i = 0; i < LOOP; i++) {
        pthread_mutex_lock(&lock);   /* kunci sebelum masuk */
        counter++;                   /* critical section — aman */
        pthread_mutex_unlock(&lock); /* buka setelah selesai */
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;

    pthread_mutex_init(&lock, NULL);

    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);

    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    pthread_mutex_destroy(&lock);

    printf("Ekspektasi : %d\n", LOOP * 2);
    printf("Hasil nyata: %d\n", counter);

    if (counter == LOOP * 2)
        printf("STATUS: Benar! Mutex melindungi critical section.\n");
    else
        printf("STATUS: Salah — ada bug di kode ini.\n");

    return 0;
}
03_spinlock.c

Spinlock dengan Instruksi Atomik Test-and-Set

Lock dibangun manual menggunakan __sync_lock_test_and_set — versi C dari instruksi hardware Test-and-Set. Hasilnya tetap benar, tapi thread yang menunggu terus memakan CPU.

spinlock test-and-set atomic instruction busy-wait __sync_lock_test_and_set
Cara kerja Test-and-Set: __sync_lock_test_and_set(&flag, 1) membaca nilai flag lama lalu langsung menulis 1 — dalam satu instruksi CPU yang tidak bisa disela. Jika nilai lama = 0, artinya kita berhasil mengambil lock. Jika nilai lama = 1, artinya orang lain duluan — kita loop dan coba lagi.
Perhatian CPU usage: jalankan ./spin lalu buka terminal lain dan ketik top. Amati bahwa proses spin menggunakan CPU mendekati 100% per core — karena thread yang menunggu tidak tidur, melainkan terus-menerus mengecek flag.
Yang perlu diobservasi
  1. Jalankan ./spin tiga kali — hasilnya selalu 2.000.000? (harus ya)
  2. Bandingkan: time ./mutex vs time ./spin — mana lebih cepat, dan seberapa besar selisihnya?
  3. Buka top saat ./spin berjalan — amati CPU usage vs saat ./mutex berjalan.
  4. Diskusikan: kapan spinlock lebih cocok dipakai daripada mutex?
/*
 * 03_spinlock.c – Spinlock dengan instruksi atomik Test-and-Set
 * Compile: gcc -Wall -pthread -O0 -o spin 03_spinlock.c
 *
 * Bandingkan kecepatan:
 *   time ./mutex
 *   time ./spin
 *
 * Pantau CPU saat spinlock berjalan:
 *   top   (amati CPU usage mendekati 100% per core)
 */
#include <stdio.h>
#include <pthread.h>

#define LOOP 1000000

int counter = 0;
int flag = 0; /* 0 = bebas, 1 = terkunci */

void spin_lock(int *f) {
    /* __sync_lock_test_and_set: baca nilai lama, lalu tulis 1 — atomik */
    while (__sync_lock_test_and_set(f, 1) == 1)
        ; /* putar terus sampai mendapat 0 (berhasil ambil lock) */
}

void spin_unlock(int *f) {
    __sync_lock_release(f); /* tulis 0 secara atomik */
}

void *increment(void *arg) {
    for (int i = 0; i < LOOP; i++) {
        spin_lock(&flag);
        counter++;
        spin_unlock(&flag);
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;

    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);

    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    printf("Ekspektasi : %d\n", LOOP * 2);
    printf("Hasil nyata: %d\n", counter);

    if (counter == LOOP * 2)
        printf("STATUS: Benar! Spinlock (Test-and-Set) berhasil.\n");
    else
        printf("STATUS: Salah — ada bug di kode ini.\n");

    return 0;
}
